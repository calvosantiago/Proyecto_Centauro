1. Resumen de Arquitectura

Centauro es un sistema de auditoría automática basado en RAG (Retrieval-Augmented Generation). En su versión 3.0, ha evolucionado de un sistema de validación binaria (Checklist) a un Modelo de Evaluación Cualitativa por Competencias.

El objetivo es diferenciar al vendedor "Robot" (que cumple el guion sin alma) del vendedor "Experto" (que persuade y conecta), utilizando una escala de 1 a 5 y validación semántica.

1.1. Flujo End-to-End (Visión Operativa)

El sistema se ejecuta de forma batch y local. El punto de entrada es main.py, que carga manuales, limpia transcripciones y orquesta la auditoría completa.

1.3. Principios de Diseño

  • Calidad sobre Cumplimiento: Se premia la ejecución experta (soft skills) sobre la repetición robótica.
  • Determinismo sobre creatividad: Temperatura 0 y JSON estricto.
  • RAG acotado: La IA solo ve fragmentos recuperados, no el manual completo.
  • Auditoría verificable: Cada conclusión debe tener evidencia textual y pasa por el Sheriff.

    • 1.4. Pipeline V4 (Extractor -> Evaluador -> Auditor)

    La versi¢n actual separa responsabilidades en tres etapas para reducir alucinaciones y mejorar justicia:

    • Extractor: Solo hechos observables con evidencia literal (sin notas).
    • Evaluador: Aplica la rúbrica usando solo lo extra¡do.
    • Auditor: Verifica evidencia (spans/fuzzy) y ajusta inconsistencias.

2. Anatomía del Prompt y Conexión API

El núcleo de la inteligencia de Centauro reside en cómo se comunica con OpenAI. No es un chat simple; es una inyección de contexto estructurada.

2.1. Conexión API (llm_client.py)

Este módulo gestiona el "handshake" con OpenAI. Se ha configurado para eliminar la creatividad y maximizar la precisión analítica.

  • Modelo: gpt-4o-mini (Optimizado para costes y alta velocidad).
  • Temperatura: 0.0.
    Justificación: Necesitamos determinismo. Ante el mismo input, la IA debe dar siempre el mismo output.
  • Response Format: { "type": "json_object" }. Forzamos a la IA a devolver exclusivamente JSON válido.
  • Control de Costes: El script registra el gasto en outputs/control_gastos.csv.

2.2. Ingeniería del Prompt (Pipeline V4)

El prompt ahora se divide en dos roles: Extractor (hechos) y Evaluador (rúbrica).

Estrategia "Pipeline V4":
Le decimos a la IA: "Primero extrae hechos observables con evidencia literal. Luego evalúa calidad usando solo esos hechos."

2.3. Prompt Extractor (hechos)

El extractor tiene prohibido evaluar. Solo devuelve eventos observables con evidencia literal copiada de la transcripción.

  • Salida estricta en JSON.
  • Anti prompt-injection: la transcripción es dato, no instrucción.
  • Marca NO_OBSERVABLE_OFF_RECORD si la llamada empieza ya avanzada.

2.4. Prompt Evaluador (rúbrica)

El evaluador solo puede usar el JSON del extractor. No puede inventar evidencia nueva.

  • Notas 1-5 por bloque + observabilidad + confianza.
  • Soft skills con evidencia distribuida (1 principal + 3-6 adicionales).
  • Legal/Apertura en OFF-RECORD no afectan la nota final.

2.5. ¿Qué es RAG y cómo se usa aquí?

RAG (Retrieval-Augmented Generation) es una técnica que combina un buscador vectorial con un modelo generativo. En Centauro, el modelo NO recibe todo el manual: solo recibe los fragmentos más relevantes recuperados de ChromaDB.

En palabras simples: primero se busca "lo más parecido" en los manuales, luego esa evidencia se adjunta al prompt para que el modelo responda con conocimiento real y no con suposiciones.

2.6. ¿Qué es ChromaDB?

ChromaDB es una base de datos vectorial local. Guarda representaciones matemáticas (embeddings) de los manuales para poder buscar por significado y no por palabras exactas. Aquí se usa en modo persistente, por eso existe la carpeta .chroma_db.

Ventaja clave: si el manual cambia, se reindexa y el sistema "recuerda" el nuevo contenido sin necesidad de reentrenar ningún modelo.

2.7. ¿Qué es un embedding y para qué sirve?

Un embedding es un vector numérico que representa el significado de un texto. Textos con ideas parecidas quedan cerca en ese espacio vectorial.

Centauro usa text-embedding-3-small para convertir cada fragmento del manual en números comparables. Luego ChromaDB busca los fragmentos más cercanos al texto de consulta.

2.8. RAG paso a paso (como funciona en este proyecto)

  1. Indexacion: Los manuales en inputs/docs se dividen en fragmentos (chunks).
  2. Embeddings: Cada fragmento se convierte en un embedding y se guarda en ChromaDB.
  3. Consulta: Antes de evaluar, se genera una consulta del tipo "Venta consultiva metodologia cierre empatia".
  4. Recuperacion: ChromaDB devuelve los Top-K fragmentos mas relevantes.
  5. Inyeccion de contexto: Esos fragmentos se insertan en el prompt dentro de <MANUAL>.
  6. Respuesta: El modelo responde usando ese contexto como referencia.

2.9. Parametros RAG configurados

  • Tamano de chunk: 1000 caracteres.
  • Solapamiento: 100 caracteres para no cortar ideas.
  • Top-K: 20 fragmentos por consulta (ajustable).

3. Matriz de Evaluación V3 (Modelo Cualitativo)

Centauro V3 introduce una diferenciación crítica entre Hard Skills (técnica) y Soft Skills (habilidades humanas), puntuadas con una rúbrica.

📏 La Rúbrica de Puntuación (1-5)

  • 1 (Deficiente): No lo hace o lo hace mal.
  • 3 (Cumplidor - Robot): Lo hace mecánicamente siguiendo el guion, pero sin empatía.
  • 5 (Excelente - Experto): Lo hace de forma natural, estratégica y persuasiva.

3.1. Competencias Técnicas (Hard Skills)

Competencia Importancia Criterio de Excelencia (Nota 5)
1. SONDEO ALTA Preguntas profundas que descubren el "dolor" real del cliente, no solo datos demográficos.
2. VALOR ALTA Adaptación de los beneficios (Ranking, Metodología) al perfil del alumno.
3. CIERRE ALTA Proactividad y seguridad al pedir el compromiso o el pago.
4. LEGAL BAJA Cumplimiento normativo estricto (Mencionar grabación).

3.2. Habilidades Blandas (Soft Skills)

Estas competencias tienen pesos CRÍTICOS porque diferencian al Top Performer.

Habilidad Importancia Criterio de Excelencia (Nota 5)
1. ESCUCHA ACTIVA CRÍTICO Validar emociones, dejar hablar y retomar palabras del cliente.
2. MANEJO OBJECIONES CRÍTICO Rebatir con inteligencia emocional y argumentos nuevos, no repetición.
3. TONO Y CONFIANZA MEDIA Transmisión de autoridad, calma y profesionalidad.

4. Metodología de Validación (Sheriff/Auditor V4)

El Auditor V4 valida evidencia, detecta contradicciones y ajusta notas sin castigar injustamente cuando hay hechos parciales.

4.1. Validación Existencial

Verifica que la evidencia citada por la IA exista realmente en el audio.

  • Si existe: Se respeta la nota de la IA.
  • Si NO existe: Se penaliza automáticamente con Nota 1 y se marca como [ALUCINACIÓN].

4.2. Validación Semántica (Anti-Fake Legal)

Para el criterio "LEGAL", el Sheriff no solo busca que la frase exista. Verifica que contenga palabras clave obligatorias: "grabar", "monitorizar", "calidad", "aviso".

Ejemplo: Si la IA cita "Este espacio es para ti" como aviso legal, el Sheriff lo rechaza (Nota 1) porque no contiene términos legales, aunque la frase sea real.

4.3. C lculo de Nota Ponderada

La nota final se calcula normalizando la escala 1-5:

Puntuaci¢n Normalizada = (Nota_IA / 5.0)
Nota Final = ( S (Puntuaci¢n_Norm * Peso) / S Pesos_Totales ) * 10

4.4. Umbral de evidencia (sheriff ligero)

La validacion existencial no busca coincidencia exacta. Se limpian tokens y se valida un ratio minimo de 0.60 entre las palabras de la cita y la transcripcion. Esto tolera pequenas variaciones del ASR (errores de transcripcion).

4.5. Auditor flexible (no todo a 1)

Si hay eventos del extractor pero falta evidencia literal perfecta, el auditor baja suavemente la nota y marca BAJA_EVIDENCIA en lugar de castigar con 1.

7. Procesos Internos y Lógica de Datos

7.1 Limpieza de transcripciones

Las transcripciones en VTT se limpian de timestamps y UUIDs para evitar ruido en el análisis cualitativo.

También se eliminan etiquetas de estilo (<v>, <b>) y se compacta el texto en una sola línea para reducir tokens y costo.

7.2 Redacción de datos personales

Antes de enviar información a la API, se sustituyen patrones sensibles por etiquetas [REDACTED_*].

Se detectan: email, teléfono, DNI, NIE e IBAN. Esta capa reduce riesgos de privacidad y cumple buenas prácticas de datos.

7.3 Generación del reporte

La IA devuelve un JSON con puntuaciones 1-5. El Auditor valida la evidencia, aplica ajustes graduales y calcula la nota final.

Luego se separan puntos fuertes (nota >= 3) y áreas de mejora (nota < 3) para el PDF ejecutivo.

8. Distribución de Carpetas

  • inputs/docs: Manuales de calidad (base RAG).
  • inputs/transcripts: Transcripciones de audio.
  • outputs: Reportes JSON, PDF y logs.
  • centauro: Núcleo lógico.

9. Deep Dive: Conexión API

Mantiene la configuración de temperature: 0.0 para garantizar que, aunque la evaluación sea cualitativa, sea consistente entre ejecuciones.

La salida se fuerza a JSON estricto (response_format: json_object) para evitar texto libre y simplificar la validacion.

El consumo de tokens se registra en outputs/control_gastos.csv con fecha, hora, tokens y costo estimado en USD.

10. Deep Dive: Ingeniería de Prompt (Pipeline V4)

El prompt V4 separa extractor (hechos) y evaluador (rúbrica) para evitar alucinaciones.

"EXTRACTOR: devuelve eventos con evidencia literal. SIN NOTAS."
"EVALUADOR: aplica rúbrica solo con esos eventos."

10.1. Penalización Automática

El sistema está diseñado para desconfiar. Si la IA otorga un 5 pero la evidencia es débil o inexistente, el código Python sobreescribe la nota a 1.

10.2. Tipo de evaluacion usada

La evaluacion es cualitativa por competencias. No se busca solo "cumplir el guion", sino la calidad real de la interaccion (empatia, persuasion, manejo de objeciones).

La escala 1-5 se interpreta como: 1=Deficiente, 3=Robot (cumple sin conectar), 5=Experto (natural y estrategico).

12. Glosario Basico (para no tecnicos)

  • LLM: Modelo de lenguaje grande. Aqui es GPT-4o-mini.
  • Prompt: Instrucciones que se le envian al modelo.
  • Token: Unidad de texto usada para medir costo.
  • Embedding: Vector numerico que representa el significado de un texto.
  • Vector DB: Base de datos que busca por similitud de significado.
  • RAG: Metodo que combina busqueda (manuales) + generacion (LLM).
  • Chunking: Dividir documentos largos en fragmentos pequenos.
  • Top-K: Numero de fragmentos mas relevantes que se recuperan.
  • Temperatura: Controla creatividad. 0 = mas determinista.
  • Observabilidad: Cuanto se puede evaluar un bloque con la evidencia disponible.
  • Confianza: Nivel de certeza del evaluador en la nota asignada.
  • OFF-RECORD: Bloque no evaluable porque ocurri¢ antes de la grabaci¢n.
