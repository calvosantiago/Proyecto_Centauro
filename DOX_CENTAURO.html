1. Resumen de Arquitectura

Centauro es un sistema de auditoria automatica basado en RAG (Retrieval-Augmented Generation) y dos pasos LLM: diarizacion y evaluacion. El objetivo es diferenciar al vendedor "Robot" (cumple el guion sin alma) del vendedor "Experto" (persuade y conecta), usando escala 1-5 con auditoria de evidencias.

1.1. Flujo End-to-End (Vision Operativa)

El sistema se ejecuta de forma batch y local. El punto de entrada es main.py, que carga manuales, limpia transcripciones y orquesta la auditoria completa.

1.3. Principios de Diseno

  • Calidad sobre cumplimiento: Se premia la ejecucion experta sobre la repeticion robotica.
  • Determinismo sobre creatividad: Temperatura 0 y JSON estricto.
  • RAG acotado: La IA solo ve fragmentos recuperados, no el manual completo.
  • Auditoria verificable: Cada conclusion debe tener evidencia textual y pasa por el Sheriff.

1.4. Pipeline actual (Diarizacion + Evaluacion + Sheriff V15)

La version actual separa diarizacion y evaluacion para mejorar atribucion, y aplica auditoria de evidencias:

  • Redaccion PII: Email, telefono, DNI/NIE e IBAN se sustituyen por etiquetas.
  • Diarizacion LLM: Etiqueta cada frase con [ASESOR] / [LEAD].
  • Evaluacion LLM: Prompt detallado con transcripcion diarizada y contexto RAG.
  • Sheriff V15: Valida evidencias con fuzzy matching y ajusta notas.
  • Salida: JSON validado + PDF ejecutivo.

2. Anatomia del Prompt y Conexion API

El nucleo de la inteligencia de Centauro reside en como se comunica con OpenAI. No es un chat simple; es una inyeccion de contexto estructurada.

2.1. Conexion API (llm_client.py)

Este modulo gestiona el "handshake" con OpenAI. Se ha configurado para eliminar la creatividad y maximizar la precision analitica.

  • Modelo: gpt-4o-mini (Optimizado para costes y alta velocidad).
  • Temperatura: 0.0.
    Justificacion: Necesitamos determinismo. Ante el mismo input, la IA debe dar siempre el mismo output.
  • Response Format: { "type": "json_object" }. Forzamos a la IA a devolver exclusivamente JSON valido.
  • Control de Costes: El script registra el gasto en outputs/control_gastos.csv.

2.5. Que es RAG y como se usa aqui?

RAG (Retrieval-Augmented Generation) es una tecnica que combina un buscador vectorial con un modelo generativo. En Centauro, el modelo NO recibe todo el manual: solo recibe los fragmentos mas relevantes recuperados de ChromaDB.

En palabras simples: primero se busca "lo mas parecido" en los manuales, luego esa evidencia se adjunta al prompt para que el modelo responda con conocimiento real y no con suposiciones.

2.6. Que es ChromaDB?

ChromaDB es una base de datos vectorial local. Guarda representaciones matematicas (embeddings) de los manuales para poder buscar por significado y no por palabras exactas. Aqui se usa en modo persistente, por eso existe la carpeta chroma_db.

Ventaja clave: si el manual cambia, se reindexa y el sistema "recuerda" el nuevo contenido sin necesidad de reentrenar ningun modelo.

2.7. Que es un embedding y para que sirve?

Un embedding es un vector numerico que representa el significado de un texto. Textos con ideas parecidas quedan cerca en ese espacio vectorial.

Centauro usa text-embedding-3-small para convertir cada fragmento del manual en numeros comparables. Luego ChromaDB busca los fragmentos mas cercanos al texto de consulta.

2.8. RAG paso a paso (como funciona en este proyecto)

  1. Indexacion: Los manuales en inputs/docs se dividen en fragmentos (chunks).
  2. Embeddings: Cada fragmento se convierte en un embedding y se guarda en ChromaDB.
  3. Consulta: Antes de evaluar, se genera una consulta del tipo "Venta consultiva metodologia cierre empatia legal".
  4. Recuperacion: ChromaDB devuelve los Top-K fragmentos mas relevantes.
  5. Inyeccion de contexto: Esos fragmentos se insertan en el prompt dentro de <MANUAL_OBS>.
  6. Respuesta: El modelo responde usando ese contexto como referencia.

2.9. Parametros RAG configurados

  • Tamano de chunk: 1000 caracteres.
  • Solapamiento: 100 caracteres para no cortar ideas.
  • Top-K: 20 fragmentos por consulta (ajustable).

3. Bloques de Evaluacion V15 (Modelo Cualitativo)

La evaluacion se organiza en 7 bloques fijos. La escala 1-5 se interpreta como: 1=Deficiente, 3=Robot (cumple sin conectar), 5=Experto (natural y estrategico).

Deteccion de necesidades Preguntas profundas, escucha y motivaciones; requiere evidencia distribuida.

4. Metodologia de Validacion (Sheriff V15)

El Sheriff V15 valida evidencia, detecta contradicciones y ajusta notas sin castigar injustamente cuando hay hechos parciales.

4.1. Validacion Existencial

Verifica que la evidencia citada por la IA exista realmente en el audio, usando coincidencia fuzzy.

  • Si existe: Se respeta la nota de la IA.
  • Si NO existe: Se ajusta la nota (de 4-5 a 3) o se penaliza a 1 si la evidencia es inexistente.

4.2. Validacion Semantica (Off-record)

Para Apertura y Legal, si no hay evidencia y parece inicio tardio, se marca NO_OBSERVABLE_OFF_RECORD y no se penaliza.

4.3. Recalculo de Nota Global

La nota global es el promedio de los bloques observables (se excluyen los no observables).

4.4. Umbral de evidencia (fuzzy)

La validacion existencial no busca coincidencia exacta. Se limpia texto y se valida un ratio minimo: 85 si la cita es corta, 60 si es larga.

4.5. Auditor flexible (no todo a 1)

Si hay evidencia parcial, el auditor ajusta a 3 en lugar de castigar con 1, salvo alucinacion clara.

7. Procesos Internos y Logica de Datos

7.1 Limpieza de transcripciones

Las transcripciones en VTT se limpian de timestamps y UUIDs para evitar ruido en el analisis cualitativo.

Tambien se eliminan etiquetas de estilo (<v>, <b>) y se compacta el texto en una sola linea para reducir tokens y costo.

7.2 Redaccion de datos personales

Antes de enviar informacion a la API, se sustituyen patrones sensibles por etiquetas [REDACTED_*].

Se detectan: email, telefono, DNI, NIE e IBAN. Esta capa reduce riesgos de privacidad y cumple buenas practicas de datos.

7.3 Diarizacion (separacion de interlocutores)

El sistema usa un prompt LLM con anclas semanticas para etiquetar cada frase como [ASESOR] o [LEAD].

Se procesa por bloques de ~3000 caracteres para manejar textos largos y se guarda una copia en outputs/Input_Debug.

7.4 Generacion del reporte

La IA devuelve un JSON con puntuaciones 1-5 y cobertura por tramos. El Sheriff valida la evidencia, aplica ajustes graduales y recalcula la nota final.

Luego se separan puntos fuertes (nota >= 3) y areas de mejora (nota < 3) para el PDF ejecutivo.

8. Distribución de Carpetas

  • inputs/docs: Manuales de calidad (base RAG).
  • inputs/transcripts: Transcripciones de audio.
  • outputs: Reportes JSON, PDF y logs.

9. Deep Dive: Conexion API

Mantiene temperature: 0.0 para garantizar consistencia entre ejecuciones.

La salida se fuerza a JSON estricto (response_format: json_object) para evitar texto libre y simplificar la validacion.

El consumo de tokens se registra en outputs/control_gastos.csv con fecha, hora, tokens y costo estimado en USD.

Hay dos llamadas LLM: diarizacion por bloques y evaluacion final con contexto RAG.

10. Deep Dive: Ingenieria de Prompt (V15)

El prompt define reglas de evidencia literal, cobertura por tramos y la regla OFF-RECORD para evitar penalizaciones injustas.

"Devuelve SOLO JSON. Citas literales con [ASESOR]/[LEAD]."
"Cobertura por tramos y alerta_cobertura si falta evidencia."

10.1. Ajuste Automatico

Si la evidencia es debil o inexistente, el Sheriff ajusta la nota (4-5 a 3) o penaliza a 1 en casos de alucinacion.

10.2. Tipo de evaluacion usada

La evaluacion es cualitativa por bloques. No se busca solo "cumplir el guion", sino la calidad real de la interaccion (empatia, persuasion, manejo de objeciones).

11. Pseudocodigo del Sheriff V15

def validar_y_auditar(bloque, audio, eventos):
    # 1. Evidencia (span o fuzzy)

12. Glosario Basico (para no tecnicos)

  • LLM: Modelo de lenguaje grande. Aqui es GPT-4o-mini.
  • Prompt: Instrucciones que se le envian al modelo.
  • Token: Unidad de texto usada para medir costo.
  • Embedding: Vector numerico que representa el significado de un texto.
  • Vector DB: Base de datos que busca por similitud de significado.
  • RAG: Metodo que combina busqueda (manuales) + generacion (LLM).
  • Chunking: Dividir documentos largos en fragmentos pequenos.
  • Top-K: Numero de fragmentos mas relevantes que se recuperan.
  • Temperatura: Controla creatividad. 0 = mas determinista.
  • Observabilidad: Cuanto se puede evaluar un bloque con la evidencia disponible.
  • Confianza: Nivel de certeza del evaluador en la nota asignada.
  • OFF-RECORD: Bloque no evaluable porque ocurri¢ antes de la grabaci¢n.
